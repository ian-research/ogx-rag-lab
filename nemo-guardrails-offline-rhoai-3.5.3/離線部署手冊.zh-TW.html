本手冊面向接收部署包的實施同事。目標環境已經安裝 OpenShift AI 3.5.3，並已提供可用的 MaaS/TinyLlama 服務。按文件部署獨立 NeMo 護欄端點並接入 Playground，可實現普通請求放行、五類輸入規則攔截，以及中文規則編號、原因和調整建議展示。

文件只包含重現所需的準備、部署、驗證和維護步驟。容器映像檔、模型權重和目標環境驗證資訊由接收方提供；無需重做原演示環境的排錯過程。

1 目標效果與部署邊界

Playground → OGX → MaaS → TinyLlama
Playground → OGX → NeMo 輸入檢查
                    ├─ 放行 → MaaS → TinyLlama
                    └─ 攔截 → 直接返回中文規則說明

兩條路徑用於獨立對照。TinyLlama 負責正常問答，通常使用英語；中文攔截文字由規則程式碼固定返回，不要求模型生成中文。規則支援大小寫不敏感匹配、簡體中文、臺灣繁體中文或英文的指定表達，以及一次請求命中多個規則。

項目基線與要求
OpenShift AI3.5.3；目標平臺已安裝並完成離線映像檔設定
OGX基線 Operator 0.13.0；必須支援 spec.tls.trust.caCertificates
模型已有 TinyLlama-1.1B-Chat-v1.0 的 MaaS 服務；上下文上限 2048
護欄實現TrustyAI 管理的 NemoGuardrails，Colang 1.0 與 Python action
管理終端Linux 或 macOS，已登入目標叢集的 oc 與 Python 3.9+；無需 pip install
驗收方式本機規則測試、服務內 HTTP、OGX 到 NeMo 的 HTTPS/RBAC、Playground 對照

本包只實現輸入規則的模式匹配，不新增輸出護欄，不使用 LLM 自檢分類器或 RAG。Playground 頁面自帶的 User input guardrails 與 Model output guardrails 在本方案中均保持關閉；選擇 NeMo 端點本身就會執行這裡的輸入規則。

2 離線環境準備

2.1 平臺與權限

使用能建立命名空間、Secret、ConfigMap、Role、RoleBinding、NemoGuardrails，並能檢視和修改 OGXServer 的實施賬號。準備一個現有 OpenShift AI 專案作為 Playground 專案；預設示例名稱為 llm。建議為護欄使用獨立命名空間，預設 nemo-guardrails-demo。

確認 TrustyAI 和 Llama Stack Operator 元件為 Managed，相關 Operator 已就緒；Dashboard 已啟用 Gen AI studio 和自定義 AI asset endpoints。若這些前提已經滿足，跳過下面兩項設定。

oc get datascienceclusters
oc get odhdashboardconfigs -A

元件啟用：將 DSC_NAME 取代為上一步顯示的現有資源名。補丁只設定本方案所需的兩個元件，保留其他元件設定。

DSC_NAME=default-dsc
oc patch datasciencecluster "$DSC_NAME" --type=merge \
  --patch-file templates/01-dsc.patch.yaml

介面入口啟用：按實際查詢結果設定 Dashboard 資源名和命名空間。執行後重新整理 OpenShift AI 頁面。

DASHBOARD_NS=redhat-ods-applications
DASHBOARD_NAME=odh-dashboard-config
oc patch odhdashboardconfig "$DASHBOARD_NAME" \
  -n "$DASHBOARD_NS" --type=merge \
  --patch-file templates/02-dashboard.patch.yaml

目標專案應具備 Playground 使用的預設或平臺指定儲存類，能夠建立並掛載資料庫 PVC。MaaS 訂閱應允許測試請求使用的模型和足夠的 token 配額。

2.2 必須提前準備的映像檔

本包沒有容器映像檔。離線管理員應按目標 OpenShift AI 3.5.3 的實際映像檔引用，將下表元件及其依賴映像檔同步到可訪問的內部倉庫，並完成映像檔對映、拉取驗證資訊和倉庫憑證設定。已有 MaaS/TinyLlama 不代表這些新增元件映像檔已經齊備。使用同版本 digest，不取代為 latest。

元件需要覆蓋的映像檔範圍
TrustyAI 與 NeMoTrustyAI Operator、NeMo 主容器、kube-rbac-proxy、憑證初始化容器
PlaygroundOGX Operator、OGX 執行階段、pgvector/PostgreSQL，以及平臺生成的其他 init/sidecar
既有服務已部署 Dashboard、MaaS 閘道器與 TinyLlama；由現有平臺提供

執行階段映像檔由已安裝的 Operator 選擇，本包不另建 Deployment 或覆蓋 Operator 映像檔設定。規則只使用 Python 標準庫；不新增需要下載權重的分類器、嵌入模型或 NLP 包。NeMo 資源中設定 HF_HUB_OFFLINE 和 TRANSFORMERS_OFFLINE，避免意外線上模型下載。完整隔離可用性仍需在目標斷網叢集驗收。

2.3 網路與憑證

NeMo → MaaS目標 MaaS 地址及埠可達，API key 有效
認證代理 → API Server允許 token 驗證及權限檢查

校驗交付檔案：Linux 使用第一條，macOS 使用第二條，二選一。校驗應在編輯檔案之前完成。

cp -n settings.example.json settings.json

編輯 settings.json。不要將任何 API key 或 token 寫進此檔案。

欄位填寫方式
playground_namespace已存在的 OpenShift AI 專案，例如 llm
nemo_namespace護欄專用命名空間，例如 nemo-guardrails-demo
nemo_nameNeMo 資源和 Service 名稱，例如 nemo-regex

maas_base_url 是 NeMo 呼叫 MaaS 的模型 API 基址，必須使用目標模型實際可用的協議、域名和完整路徑。AI asset endpoints 的 MaaS 彈窗可能只顯示閘道器根地址，該根地址不能直接替代模型 API 路徑。示例形態為 http(s)://maas.apps.<叢集域名>/<專案>/<模型路由>/v1，具體路徑以目標 MaaS 為準；不要自行將 http 改成 https。

Playground 中新增端點填寫的是 NeMo Service 的 HTTPS 地址，與 maas_base_url 不同。model_id 使用 API 模型 ID，不使用顯示名稱或 Playground 的 endpoint-1 字首。

維護已有本方案部署時，可只讀檢視現有設定中的 base_url，核對後填入 settings.json；首次部署請從目標 MaaS 的可用呼叫設定獲取。命名空間如有調整，下面指令同步修改。

oc get configmap nemo-demo-rules-config \
  -n nemo-guardrails-demo \
  -o jsonpath='{.data.config\.yaml}' | grep 'base_url:'
python3 scripts/render.py
python3 -m unittest discover -s tests -v
python3 scripts/cluster.py preflight

渲染結果位於 rendered/。確認其中沒有未取代的目標環境參數。本機測試應顯示 41 個測試方法透過，包含全部 58 條規則用例在兩種提示語言下的檢查，以及設定初始化、目標專案檢查、Playground 就緒判斷、token 到期時間儲存和指定驗證資訊驗證。叢集呼叫與 HTTP 響應在本機測試中使用模擬資料，不代表目標叢集已透過驗收。預檢檢查目標專案、NeMo/OGX CRD 與所需憑證欄位，不代替映像檔、Operator 就緒和儲存檢查。

不要執行 oc apply -f rendered。該目錄同時包含獨立資源、merge patch 和未填寫的 Secret 示例；必須按後文選擇檔案執行，或使用分階段指令碼。

3.2 選擇中文提示語言

新建臺灣繁體部署時，可以用下面指令替代前面的簡體樣例複製指令；只選其中一個樣例。已有 settings.json 時，直接新增或修改 response_language 為 zh-TW，保留其他欄位，不要用樣例覆蓋現有設定。

4 部署 NeMo 服務

4.1 首次安裝

python3 scripts/cluster.py install

按終端提示輸入目標 MaaS API key，輸入不會顯示。指令碼將其寫入護欄命名空間的 tinyllama-maas-api-key Secret，鍵名為 token。該 key 用於 NeMo 呼叫 MaaS，與後面訪問 NeMo 的服務帳號 token 不同。不要在 key 前增加 Bearer。

指令碼依次建立命名空間、訪問賬號與 RBAC、MaaS Secret、最終業務規則 ConfigMap、可選上游 CA、NemoGuardrails 資源和 Playground Service CA ConfigMap。隨後等待 NeMo 可用，並確認容器載入的是本次設定檔案。已存在同名 NeMo 資源時，install 停止，避免將首次安裝指令用於覆蓋既有部署。

資源中的 basic 是 NeMo 設定 ID，引用 nemo-demo-rules-config。該 ConfigMap 在安裝時已經包含最終五類規則；不需要先建立 NEMO_BLOCK_TEST 舊設定，也不需要修改 llm/guardrail-placeholder。

python3 scripts/cluster.py verify-service

此步驟從 NeMo 容器內部測試六個獨立請求：測試標記、混合大小寫、雙規則命中、簡體驗證資訊、臺灣繁體客戶明細和普通問答。全部顯示 PASS 後再接入 Playground。每次請求使用獨立訊息列表，普通問答允許最長 180 秒。

4.2 服務地址和認證

預設參數下，自定義端點 API 基址為下列地址；如果更改了 nemo_name 或 nemo_namespace，使用指令碼安裝完成後列印的對應地址。無需額外建立 Route。

https://nemo-regex.nemo-guardrails-demo.svc.cluster.local/v1
python3 scripts/cluster.py token --duration=720h

指令碼為 nemo-playground-client 服務帳號申請 720 小時（30 天）token；省略 --duration 時預設也是 720h。原始 token 儲存在 private/nemo-playground-token.txt，檔案權限為 0600，終端不直接列印 token。將該檔案內容用於自定義端點 API key，不加 Bearer，也不能使用 MaaS API key 替代。

30 天是申請時長，不保證叢集一定按此時長簽發；實際可能更短或更長。不要用“生成日期加 30 天”推算到期日，按下一節檢查實際簽發結果。private/ 含驗證資訊或備份，不屬於對外交付內容。

RBAC 只授予該賬號在護欄命名空間 get services 的權限。認證代理執行的是命名空間級 services 權限檢查，模板不附加 resourceNames 限制。

4.3 檢查實際到期時間

生成 token 時，指令碼讀取 API Server 返回的 status.expirationTimestamp，列印 UTC 和北京時間，並另存一份不含 token 的到期記錄。之後可用下面的指令檢視，無需再次申請 token。

cat private/nemo-playground-token-info.json

記錄中的 requested_duration 是申請時長，expirationTimestamp 是叢集返回的實際到期時間（Z 表示 UTC），expires_at_beijing 是同一時刻的北京時間（+08:00）。該記錄對應最近一次由本指令碼儲存的 token；只有將對應 token 設定到端點後，它才代表 Playground 所用驗證資訊的到期時間。

如果不使用指令碼，可直接執行下面的等效申請指令。第一行輸出實際 UTC 到期時間，第二行輸出新 token。該指令會簽發新 token，不是查詢 Playground 中舊 token 的到期時間；複製驗證資訊時只複製第二行。命名空間如有變化需同步取代。

oc create token nemo-playground-client \
  -n nemo-guardrails-demo \
  --duration=720h \
  -o jsonpath='{.status.expirationTimestamp}{"\n"}{.status.token}{"\n"}'

5 在 Playground 新增端點

使用已具備專案訪問權限的賬號登入 OpenShift AI。進入 Gen AI studio → AI asset endpoints，選擇 settings.json 中的 playground_namespace，點選 Create endpoint，按下表填寫。

介面欄位填寫值
Model IDsettings.json 中的 model_id，區分大小寫
Display nameTinyLlama + NeMo Guardrails；專案內名稱唯一
Endpoint URL上一節的 NeMo HTTPS Service 地址，包含 /v1
API key or tokenprivate/nemo-playground-token.txt 的原始 token，不加 Bearer

使用已知模型 ID 手動設定此端點，不把 NeMo 的模型列表自動發現作為本方案前提。保留專案中原有的 MaaS/TinyLlama 端點，用於無此護欄的對照測試。若原始模型透過 MaaS 展示，選擇有權限且配額足夠的訂閱。

Verify model 是獨立驗證按鈕；本版本 Create 不以驗證成功為前置條件。填寫完成後點選 Create 儲存端點，再繼續設定 Playground。建立成功只表示端點已登記，連通性與驗證資訊仍以第 6—7 節驗收為準；通用的 Verification failed 提示本身不能確定原因。

進入 Playground，透過建立或 Configure playground 視窗勾選原始 TinyLlama 與 TinyLlama + NeMo Guardrails。兩個模型均選擇 Inference，Max tokens 均填 128，然後完成設定並等待 Playground 後端建立。

這裡的 128 是 Playground 模型設定上限；NeMo ConfigMap 中保留主模型預設 max_tokens 64。兩者作用層次不同，不必設定成同一個數。短輸入測試必須滿足實際輸入 token 與輸出額度合計不超過 TinyLlama 的 2048 上下文。

在右側 Model 設定中，Temperature 可設 0.1，Streaming 可開啟。原生 User input guardrails 與 Model output guardrails 均關閉；本方案的護欄由所選 NeMo 端點執行。Knowledge 與 MCP 不參與驗收。

6 設定 Playground 到 NeMo 的憑證信任

完成所有模型選擇與 Max tokens 設定後，再執行本節。先確認實際 OGXServer 名稱；下面的 llm 取代為 playground_namespace。

oc get ogxservers -n llm

若資源不存在，先回到同一專案的 Playground 完成模型選擇並點選 Configure；只建立 AI asset endpoint 不會建立 OGXServer。若資源名不同，修改 settings.json 後重新執行 render.py。其他專案中存在同名 OGXServer，不能替代當前專案的後端。

python3 scripts/cluster.py wait-playground
python3 scripts/cluster.py trust

wait-playground 同時等待 OGX 的 Ready 狀態和同名 Deployment 完成就緒。剛建立時的 Initializing 不代表失敗；指令碼最多等待 600 秒。資源不存在或狀態 Failed 時會停止並提示檢查位置，超時後需檢查 Pod、事件、映像檔和儲存就緒情況。trust 自身也包含相同的前置等待，不會在目標 Playground 缺失時先應用 CA。

指令碼等待 nemo-service-ca 注入 service-ca.crt，在現有 OGXServer 的 spec.tls.trust.caCertificates 中追加此引用，保留其他 CA 與 TLS 用戶端身份設定。修改前的物件儲存在 private/ogx-before-trust.json。指令碼使用資源版本檢查避免覆蓋併發更新，並實際從 OGX 容器驗證 NeMo HTTPS 憑證。

預期輸出包含“Playground 到 NeMo 的 TLS 验证通过”。之後執行完整接入驗證。

python3 scripts/cluster.py verify \
  --token-file private/nemo-playground-token.txt

此步驟使用指定檔案中的同一枚 token，從 OGX 容器經 NeMo HTTPS Service 傳送六個獨立請求，驗證 TLS、RBAC、規則執行與普通請求放行；不會另籤 token。每個請求超時為 180 秒，外層等待預留六次請求的總預算。此驗證不會讀取 Dashboard 儲存的驗證資訊，因此還需第 7 節的頁面驗收，確認端點中確實貼上了這枚 token。

若只需獨立檢查服務鏈路，可不帶 --token-file 執行 verify；此時會另行申請 15 分鐘臨時 token，透過檢查不能證明 Playground 儲存的舊 token 仍然有效。HTTP 驗證失敗時只顯示狀態碼或固定診斷，不列印 token 或上游響應正文。

在本版本使用 Configure playground 重新設定模型後，需要再次執行 trust 和 verify。將這兩步作為設定完成後的固定步驟，可保證新建 Playground 後端也持有 Service CA 信任。僅修改 NeMo 規則不需要重新設定 Playground。

8 規則維護與 YAML 操作

8.1 修改規則

rules/actions.py 中的 RULES 是規則定義入口，每項包含 id、name、reason、suggestion 和 patterns，以及 zh-TW 下的臺灣繁體名稱、原因和建議。MESSAGES 定義兩種語言的標題與處理結果。patterns 由兩種提示語言共用，修改文案不會改變匹配條件。匹配時先進行 NFKC 規範化和空白歸一，再使用大小寫不敏感的正則；命中列表按定義順序去重展示。rules/demo_rules.co 決定命中後的返回與停止行為。

修改規則時，同步更新 rules/cases.json 的正反例。本版包含 58 條用例，並分別驗證兩種提示語言；如果增加用例，需要相應更新 tests/test_package.py 中的數量斷言。先備份當前規則 ConfigMap，再渲染、測試和應用單個規則檔案。

mkdir -p private
chmod 700 private
umask 077
oc get configmap nemo-demo-rules-config \
  -n nemo-guardrails-demo -o yaml \
  > private/rules-before-change.yaml
python3 scripts/render.py
python3 -m unittest discover -s tests -v
oc apply -f rendered/20-rules-configmap.yaml

等待 Operator 更新 NeMo Pod 並載入新規則，再執行 verify-service 與 verify，最後用新聊天覆測。不要直接修改容器內檔案；它們會在 Pod 重建後消失。不要為規則變更重新執行 install，也不要修改 guardrail-placeholder。

oc rollout status deployment/nemo-regex \
  -n nemo-guardrails-demo --timeout=300s
python3 scripts/cluster.py verify-service
python3 scripts/cluster.py verify

rollout status 可能在 Operator 尚未處理變更時返回舊部署就緒。應用後應確認出現新 Pod 或對應部署修訂，再執行介面驗收；介面結果才是規則生效的驗收依據。需要回退規則時，應用儲存的 rules-before-change.yaml，等待新部署後重跑驗證。

8.2 不使用安裝指令碼時的 YAML 順序

仍然先填寫 settings.json 並執行 render.py。按照以下順序執行；Secret 中必須使用目標 MaaS API key。該路徑與 install 二選一，不要重複部署。

oc apply -f rendered/00-namespace.yaml
oc apply -f rendered/10-client-rbac.yaml

把 API key 儲存為權限 0600 的 private/maas-api-key 檔案，內容只包含 key。以檔案建立 Secret，避免將 key 寫入指令行歷史。

oc create secret generic tinyllama-maas-api-key \
  -n nemo-guardrails-demo \
  --from-file=token=private/maas-api-key \
  --dry-run=client -o yaml | oc apply -f -

僅當設定了私有 MaaS CA 時，先應用 rendered/21-maas-ca.yaml。隨後應用規則和 NeMo 資源。

oc apply -f rendered/20-rules-configmap.yaml
oc apply -f rendered/30-nemo.yaml
oc apply -f rendered/40-playground-service-ca.yaml

後續仍按第 4 至 7 節獲取 token、設定 Playground、執行 trust 和驗收。41-ogx-trust.patch.yaml 是補丁格式，不是可直接建立的資源；推薦使用 trust 指令碼，因為它會保留原有 CA 列表。namespace、資源名如有修改，手工指令也要同步取代。

8.3 token 到期前或過期後的更新

更新分為“申請新 token”和“讓 Playground 使用新驗證資訊”兩步。重新簽發不會延長舊 token 的有效期，也不會自動更新端點；未到期的舊 token 不會僅因簽發了新 token 就被撤銷。建議在第 4.3 節記錄的實際到期時間之前完成更新。

步驟 1：先完成第 3 節的設定初始化。新解壓包不包含 settings.json，不能直接執行續期或 trust；複製並填寫參數後執行 render.py。已有參數檔案時核對原有專案、NeMo 名稱、OGX 名稱及 MaaS 完整基址，不改用其他專案的 Playground。隨後確認 oc 當前叢集，申請新的 30 天 token 並檢查實際到期記錄。此操作覆蓋本機 token 檔案，不修改叢集中的端點設定。

oc whoami --show-server
python3 scripts/cluster.py token --duration=720h
cat private/nemo-playground-token-info.json

步驟 2：本手冊核對的 RHOAI 3.5 自定義端點列表僅提供刪除操作，沒有直接編輯 API key 的入口。因此採用建立替代端點的方法：在 Gen AI studio → AI asset endpoints 中選擇原 Playground 專案，點選 Create endpoint。沿用原 NeMo API 基址及模型 ID，使用新的唯一顯示名稱，例如 TinyLlama + NeMo Guardrails - renewed，將 private/nemo-playground-token.txt 中的新 token 填入 API key，不加 Bearer。暫時保留舊端點。

不要修改護欄命名空間中的 tinyllama-maas-api-key Secret：它儲存的是 NeMo 呼叫 MaaS 的上游驗證資訊，不是本次續期的 NeMo 訪問 token。建立替代端點只新增 Dashboard 的端點登記，不重建 NeMo 服務或規則。

步驟 3：進入 Configure playground，取消勾選舊 NeMo 端點，勾選新建的替代端點。保留原始 MaaS/TinyLlama 的選擇，把兩個所選模型的 Max tokens 都設為 128，再儲存設定並等待後端就緒。不要沿用新條目的預設 token 上限。

步驟 4：完成 Playground 設定後，等待後端就緒，補充憑證信任，並使用剛生成的 token 驗證服務鏈路。

python3 scripts/cluster.py wait-playground
python3 scripts/cluster.py trust
python3 scripts/cluster.py verify \
  --token-file private/nemo-playground-token.txt

步驟 5：重新整理 Playground 並建立新聊天，選擇新端點；保持原生輸入/輸出護欄開關關閉。先傳送 NEMO_BLOCK_TEST，確認顯示 DEMO-000 攔截說明，再傳送 Hello，確認普通請求得到模型回答。這一步用於確認 Playground 儲存的新驗證資訊實際可用。不要在繫結舊端點的歷史聊天裡繼續驗證。

新端點完成頁面驗收後，如舊端點已無其他 Playground 使用，再到 AI asset endpoints 刪除舊登記。刪除舊登記並不等於撤銷其 token，舊 token 仍按自己的實際到期時間失效。不要為 token 更新刪除服務帳號、NeMo 資源、規則 ConfigMap 或憑證；也不需要重新執行 install。

8.4 已刪除端點或 Playground 時恢復入口

本節適用於 NeMo 服務與設定仍存在，只刪除了 Dashboard 自定義端點或 Playground 的情況。先完成第 3 節的參數初始化與渲染，再確認目標服務和賬號仍在。以下使用預設名稱；自定義名稱需同步取代。

oc get nemoguardrails nemo-regex -n nemo-guardrails-demo
oc get service nemo-regex -n nemo-guardrails-demo
oc get serviceaccount nemo-playground-client -n nemo-guardrails-demo
python3 scripts/cluster.py verify-service

服務內部驗證透過後，執行 token 生成新的 NeMo 訪問驗證資訊；按第 5 節在原專案建立 NeMo 自定義端點，選擇現有 MaaS 模型與 NeMo 端點，並將兩者 Max tokens 都設為 128。Playground 已刪除時，需要重新點選 Configure 建立後端；僅儲存 endpoint 不夠。

python3 scripts/cluster.py token --duration=720h

完成介面設定後，核對同一專案中的 OGX 名稱，依次執行 wait-playground、trust 和帶 --token-file 的 verify，再用新聊天做第 7 節驗收。這條恢復路徑不執行 install，也不觸碰上游 MaaS 驗證資訊。若 NeMo 或服務帳號本身已刪除，應先核對剩餘資源並按首次部署流程恢復，不能僅重建 Dashboard 入口。

8.5 升級部署包或切換提示語言

將新版解壓到新目錄，保留舊 settings.json、private/ 和自定義規則。把舊參數複製到新目錄並核對；如需臺灣繁體，在 settings.json 中設定 response_language 為 zh-TW，需要簡體時設定為 zh-CN。先合併自己的規則改動，再執行第 8.1 節的備份、渲染、本機測試和單個 ConfigMap 應用步驟。不要用新版示例覆蓋自定義策略。

等 Operator 載入新規則後，執行下面兩項驗收。現有 token 檔案仍有效時繼續使用；若儲存在舊目錄，可把 --token-file 改為原檔案的完整路徑。僅切換提示語言不需要重建 Playground、重新安裝 NeMo 或簽發新 token。

python3 scripts/cluster.py verify-service
python3 scripts/cluster.py verify \
  --token-file private/nemo-playground-token.txt

最後在 Playground 新建聊天，傳送 NEMO_BLOCK_TEST，檢查 zh-TW 顯示“已攔截／觸發規則”，zh-CN 顯示“已拦截／命中规则”；再測試普通問題。若提示語言仍舊，先核對 rendered/20-rules-configmap.yaml 的 RESPONSE_LANGUAGE 和實際 Pod 是否已載入新設定。

9 交付狀態與使用限制

本包以已經完成的同版本功能演示為基礎，重新整理為參數化的首次部署流程。交付前已執行本機規則測試、YAML 解析與嵌入原始碼一致性檢查、指令碼語法檢查和文件排版檢查。沒有連線接收方目標叢集，也沒有聲稱已完成另一套離線叢集的端到端部署；接收方應按第 7 節記錄實際驗收結果。

規則屬於可解釋的模式匹配示例。相同關鍵表達在引用或討論場景也可能被匹配，同義改寫、編碼或混淆可能漏檢。DLP-202 表示本演示的業務策略，不執行真實客戶資料訪問或權限判斷。

不同環境應保持相同規則原始碼、NeMo/OGX 映像檔版本、MaaS 模型 ID 和設定。輸出文字與響應時間可能隨模型取樣、CPU 資源、會話歷史及 MaaS 配額變化；這些變化不等於護欄規則失效。
