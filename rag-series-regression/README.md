## 回归时逐步记录

1. 文档端按 `policy_id`、`scope`、`as_of` 检索，保存实际选中的版本和来源。
2. 员工端准备草稿，保存这次真实工具步骤。确认草稿是否真的带回上述条款；单独一次检索成功不会自动绑定进另一份草稿。
3. 预览第1版并确认，修改理由，再用真实旧确认尝试提交；应拒绝沿用旧确认。重新预览并确认当前版。
4. 明确提交一张模拟待审核申请，回读理由、资产、缺项、来源快照、版本与内容摘要。重复同一次提交应回到同一张单。
5. 两个身份先能读取自己的记录，再检查交叉访问，避免拿不存在的数据作负向检查。
6. 用草稿编号关联不同请求的 Trace，分别导出。指标与模型解释是诊断记录，不能替代申请和工单的持久状态。

这是会生成实验草稿和模拟工单的操作流程，应在已授权的演示环境逐步执行；不接真实 ITSM。文件解析与历史评测沿用前几篇证据，本轮没有重新覆盖所有文件格式或做生产压力测试。

## 离线核对保存的响应

`audit_regression.py` 只读取采集文件，不联网、不调用模型、不写工单；Python 3.12 标准库即可。输入结构以[合成示例](examples/regression.synthetic.json)和测试为准，需含一次 ask、改稿、旧确认提交、新提交、重复提交与工单回读的记录。

```bash
python3.12 audit_regression.py /path/to/saved-regression.json \
  --out /path/to/new-audit.json
```

它核对内容摘要、身份字段、草稿版本、资产、理由、事实、缺项、文档快照及返回工单号。每次输出用新文件，避免覆盖旧核对。**它不能补出未采集的数据库计数或 HTTP 响应，也不能用已有字段证明身份认证的完整性。**

本轮实际申请保留“实际使用年限、维修成本、适用文档依据”三个缺项，受理为 `pending_review`。单独文档查询成功与本次草稿 `not_retrieved` 同时成立；不把另一次查询结果补写为本次引用。
