本手册面向接收部署包的实施同事。目标环境已经安装 OpenShift AI 3.5.3，并已提供可用的 MaaS/TinyLlama 服务。按文档部署独立 NeMo 护栏端点并接入 Playground，可实现普通请求放行、五类输入规则拦截，以及中文规则编号、原因和修改建议展示。

文档只包含复现所需的准备、部署、验证和维护步骤。容器镜像、模型权重和目标环境凭据由接收方提供；无需重做原演示环境的排错过程。

1 目标效果与部署边界

Playground → OGX → MaaS → TinyLlama
Playground → OGX → NeMo 输入检查
                    ├─ 放行 → MaaS → TinyLlama
                    └─ 拦截 → 直接返回中文规则说明

两条路径用于独立对照。TinyLlama 负责正常问答，通常使用英语；中文拦截文字由规则代码固定返回，不要求模型生成中文。规则支持大小写不敏感匹配、简体中文、台湾繁体中文或英文的指定表达，以及一次请求命中多个规则。

项目基线与要求
OpenShift AI3.5.3；目标平台已安装并完成离线镜像配置
OGX基线 Operator 0.13.0；必须支持 spec.tls.trust.caCertificates
模型已有 TinyLlama-1.1B-Chat-v1.0 的 MaaS 服务；上下文上限 2048
护栏实现TrustyAI 管理的 NemoGuardrails，Colang 1.0 与 Python action
管理终端Linux 或 macOS，已登录目标集群的 oc 与 Python 3.9+；无需 pip install
验收方式本地规则测试、服务内 HTTP、OGX 到 NeMo 的 HTTPS/RBAC、Playground 对照

本包只实现输入规则的模式匹配，不新增输出护栏，不使用 LLM 自检分类器或 RAG。Playground 页面自带的 User input guardrails 与 Model output guardrails 在本方案中均保持关闭；选择 NeMo 端点本身就会执行这里的输入规则。

2 离线环境准备

2.1 平台与权限

使用能创建命名空间、Secret、ConfigMap、Role、RoleBinding、NemoGuardrails，并能查看和修改 OGXServer 的实施账号。准备一个现有 OpenShift AI 项目作为 Playground 项目；默认示例名称为 llm。建议为护栏使用独立命名空间，默认 nemo-guardrails-demo。

确认 TrustyAI 和 Llama Stack Operator 组件为 Managed，相关 Operator 已就绪；Dashboard 已启用 Gen AI studio 和自定义 AI asset endpoints。若这些前提已经满足，跳过下面两项配置。

oc get datascienceclusters
oc get odhdashboardconfigs -A

组件启用：将 DSC_NAME 替换为上一步显示的现有资源名。补丁只设置本方案所需的两个组件，保留其他组件配置。

DSC_NAME=default-dsc
oc patch datasciencecluster "$DSC_NAME" --type=merge \
  --patch-file templates/01-dsc.patch.yaml

界面入口启用：按实际查询结果设置 Dashboard 资源名和命名空间。执行后刷新 OpenShift AI 页面。

DASHBOARD_NS=redhat-ods-applications
DASHBOARD_NAME=odh-dashboard-config
oc patch odhdashboardconfig "$DASHBOARD_NAME" \
  -n "$DASHBOARD_NS" --type=merge \
  --patch-file templates/02-dashboard.patch.yaml

目标项目应具备 Playground 使用的默认或平台指定存储类，能够创建并挂载数据库 PVC。MaaS 订阅应允许测试请求使用的模型和足够的 token 配额。

2.2 必须提前准备的镜像

本包没有容器镜像。离线管理员应按目标 OpenShift AI 3.5.3 的实际镜像引用，将下表组件及其依赖镜像同步到可访问的内部仓库，并完成镜像映射、拉取凭据和仓库证书配置。已有 MaaS/TinyLlama 不代表这些新增组件镜像已经齐备。使用同版本 digest，不替换为 latest。

组件需要覆盖的镜像范围
TrustyAI 与 NeMoTrustyAI Operator、NeMo 主容器、kube-rbac-proxy、证书初始化容器
PlaygroundOGX Operator、OGX 运行时、pgvector/PostgreSQL，以及平台生成的其他 init/sidecar
既有服务已部署 Dashboard、MaaS 网关与 TinyLlama；由现有平台提供

运行时镜像由已安装的 Operator 选择，本包不另建 Deployment 或覆盖 Operator 镜像配置。规则只使用 Python 标准库；不新增需要下载权重的分类器、嵌入模型或 NLP 包。NeMo 资源中设置 HF_HUB_OFFLINE 和 TRANSFORMERS_OFFLINE，避免意外在线模型下载。完整隔离可用性仍需在目标断网集群验收。

2.3 网络与证书

连接要求
管理终端 → API Serveroc 登录和资源管理可用
OGX → NeMo Service跨命名空间 TCP 443 可达；允许集群 DNS 查询
NeMo → MaaS目标 MaaS 地址及端口可达，API key 有效
认证代理 → API Server允许 token 验证及权限检查

编辑 settings.json。不要将任何 API key 或 token 写进此文件。

字段填写方式
playground_namespace已存在的 OpenShift AI 项目，例如 llm

maas_base_url 是 NeMo 调用 MaaS 的模型 API 基址，必须使用目标模型实际可用的协议、域名和完整路径。AI asset endpoints 的 MaaS 弹窗可能只显示网关根地址，该根地址不能直接替代模型 API 路径。示例形态为 http(s)://maas.apps.<集群域名>/<项目>/<模型路由>/v1，具体路径以目标 MaaS 为准；不要自行将 http 改成 https。

Playground 中新增端点填写的是 NeMo Service 的 HTTPS 地址，与 maas_base_url 不同。model_id 使用 API 模型 ID，不使用显示名称或 Playground 的 endpoint-1 前缀。

维护已有本方案部署时，可只读查看现有配置中的 base_url，核对后填入 settings.json；首次部署请从目标 MaaS 的可用调用配置获取。命名空间如有调整，下面命令同步修改。

oc get configmap nemo-demo-rules-config \
  -n nemo-guardrails-demo \
  -o jsonpath='{.data.config\.yaml}' | grep 'base_url:'
python3 scripts/render.py
python3 -m unittest discover -s tests -v
python3 scripts/cluster.py preflight

新建台湾繁体部署时，可以用下面命令替代前面的简体样例复制命令；只选其中一个样例。已有 settings.json 时，直接新增或修改 response_language 为 zh-TW，保留其他字段，不要用样例覆盖现有配置。

4 部署 NeMo 服务

4.1 首次安装

python3 scripts/cluster.py install

按终端提示输入目标 MaaS API key，输入不会显示。脚本将其写入护栏命名空间的 tinyllama-maas-api-key Secret，键名为 token。该 key 用于 NeMo 调用 MaaS，与后面访问 NeMo 的服务账号 token 不同。不要在 key 前增加 Bearer。

脚本依次创建命名空间、访问账号与 RBAC、MaaS Secret、最终业务规则 ConfigMap、可选上游 CA、NemoGuardrails 资源和 Playground Service CA ConfigMap。随后等待 NeMo 可用，并确认容器加载的是本次配置文件。已存在同名 NeMo 资源时，install 停止，避免将首次安装命令用于覆盖既有部署。

资源中的 basic 是 NeMo 配置 ID，引用 nemo-demo-rules-config。该 ConfigMap 在安装时已经包含最终五类规则；不需要先创建 NEMO_BLOCK_TEST 旧配置，也不需要修改 llm/guardrail-placeholder。

python3 scripts/cluster.py verify-service

此步骤从 NeMo 容器内部测试六个独立请求：测试标记、混合大小写、双规则命中、简体凭据、台湾繁体客户明细和普通问答。全部显示 PASS 后再接入 Playground。每次请求使用独立消息列表，普通问答允许最长 180 秒。

4.2 服务地址和认证

默认参数下，自定义端点 API 基址为下列地址；如果更改了 nemo_name 或 nemo_namespace，使用脚本安装完成后打印的对应地址。无需额外创建 Route。

https://nemo-regex.nemo-guardrails-demo.svc.cluster.local/v1
python3 scripts/cluster.py token --duration=720h

脚本为 nemo-playground-client 服务账号申请 720 小时（30 天）token；省略 --duration 时默认也是 720h。原始 token 保存在 private/nemo-playground-token.txt，文件权限为 0600，终端不直接打印 token。将该文件内容用于自定义端点 API key，不加 Bearer，也不能使用 MaaS API key 替代。

30 天是申请时长，不保证集群一定按此时长签发；实际可能更短或更长。不要用“生成日期加 30 天”推算到期日，按下一节检查实际签发结果。private/ 含凭据或备份，不属于对外交付内容。

RBAC 只授予该账号在护栏命名空间 get services 的权限。认证代理执行的是命名空间级 services 权限检查，模板不附加 resourceNames 限制。

4.3 检查实际到期时间

生成 token 时，脚本读取 API Server 返回的 status.expirationTimestamp，打印 UTC 和北京时间，并另存一份不含 token 的到期记录。之后可用下面的命令查看，无需再次申请 token。

cat private/nemo-playground-token-info.json

记录中的 requested_duration 是申请时长，expirationTimestamp 是集群返回的实际到期时间（Z 表示 UTC），expires_at_beijing 是同一时刻的北京时间（+08:00）。该记录对应最近一次由本脚本保存的 token；只有将对应 token 配置到端点后，它才代表 Playground 所用凭据的到期时间。

如果不使用脚本，可直接执行下面的等效申请命令。第一行输出实际 UTC 到期时间，第二行输出新 token。该命令会签发新 token，不是查询 Playground 中旧 token 的到期时间；复制凭据时只复制第二行。命名空间如有变化需同步替换。

oc create token nemo-playground-client \
  -n nemo-guardrails-demo \
  --duration=720h \
  -o jsonpath='{.status.expirationTimestamp}{"\n"}{.status.token}{"\n"}'

5 在 Playground 添加端点

使用已具备项目访问权限的账号登录 OpenShift AI。进入 Gen AI studio → AI asset endpoints，选择 settings.json 中的 playground_namespace，点击 Create endpoint，按下表填写。

界面字段填写值
Model IDsettings.json 中的 model_id，区分大小写
Display nameTinyLlama + NeMo Guardrails；项目内名称唯一
Endpoint URL上一节的 NeMo HTTPS Service 地址，包含 /v1
API key or tokenprivate/nemo-playground-token.txt 的原始 token，不加 Bearer

使用已知模型 ID 手动配置此端点，不把 NeMo 的模型列表自动发现作为本方案前提。保留项目中原有的 MaaS/TinyLlama 端点，用于无此护栏的对照测试。若原始模型通过 MaaS 展示，选择有权限且配额足够的订阅。

Verify model 是独立验证按钮；本版本 Create 不以验证成功为前置条件。填写完成后点击 Create 保存端点，再继续配置 Playground。创建成功只表示端点已登记，连通性与凭据仍以第 6—7 节验收为准；通用的 Verification failed 提示本身不能确定原因。

进入 Playground，通过创建或 Configure playground 窗口勾选原始 TinyLlama 与 TinyLlama + NeMo Guardrails。两个模型均选择 Inference，Max tokens 均填 128，然后完成配置并等待 Playground 后端创建。

这里的 128 是 Playground 模型配置上限；NeMo ConfigMap 中保留主模型默认 max_tokens 64。两者作用层次不同，不必设置成同一个数。短输入测试必须满足实际输入 token 与输出额度合计不超过 TinyLlama 的 2048 上下文。

在右侧 Model 设置中，Temperature 可设 0.1，Streaming 可开启。原生 User input guardrails 与 Model output guardrails 均关闭；本方案的护栏由所选 NeMo 端点执行。Knowledge 与 MCP 不参与验收。

6 配置 Playground 到 NeMo 的证书信任

完成所有模型选择与 Max tokens 设置后，再执行本节。先确认实际 OGXServer 名称；下面的 llm 替换为 playground_namespace。

oc get ogxservers -n llm

若资源不存在，先回到同一项目的 Playground 完成模型选择并点击 Configure；只创建 AI asset endpoint 不会创建 OGXServer。若资源名不同，修改 settings.json 后重新运行 render.py。其他项目中存在同名 OGXServer，不能替代当前项目的后端。

python3 scripts/cluster.py wait-playground
python3 scripts/cluster.py trust

wait-playground 同时等待 OGX 的 Ready 状态和同名 Deployment 完成就绪。刚创建时的 Initializing 不代表失败；脚本最多等待 600 秒。资源不存在或状态 Failed 时会停止并提示检查位置，超时后需检查 Pod、事件、镜像和存储就绪情况。trust 自身也包含相同的前置等待，不会在目标 Playground 缺失时先应用 CA。

脚本等待 nemo-service-ca 注入 service-ca.crt，在现有 OGXServer 的 spec.tls.trust.caCertificates 中追加此引用，保留其他 CA 与 TLS 客户端身份配置。修改前的对象保存在 private/ogx-before-trust.json。脚本使用资源版本检查避免覆盖并发更新，并实际从 OGX 容器验证 NeMo HTTPS 证书。

预期输出包含“Playground 到 NeMo 的 TLS 验证通过”。之后执行完整接入验证。

python3 scripts/cluster.py verify \
  --token-file private/nemo-playground-token.txt

此步骤使用指定文件中的同一枚 token，从 OGX 容器经 NeMo HTTPS Service 发送六个独立请求，验证 TLS、RBAC、规则执行与普通请求放行；不会另签 token。每个请求超时为 180 秒，外层等待预留六次请求的总预算。此验证不会读取 Dashboard 保存的凭据，因此还需第 7 节的页面验收，确认端点中确实粘贴了这枚 token。

若只需独立检查服务链路，可不带 --token-file 运行 verify；此时会另行申请 15 分钟临时 token，通过检查不能证明 Playground 保存的旧 token 仍然有效。HTTP 验证失败时只显示状态码或固定诊断，不打印 token 或上游响应正文。

在本版本使用 Configure playground 重新配置模型后，需要再次执行 trust 和 verify。将这两步作为配置完成后的固定步骤，可保证新建 Playground 后端也持有 Service CA 信任。仅修改 NeMo 规则不需要重新配置 Playground。

7 验收与演示

创建两个相互独立的新聊天：第一个选择原始 MaaS 模型，第二个选择 TinyLlama + NeMo Guardrails。每组使用完全相同的输入。停止上一条正在生成的回复后再进行下一组测试；不要在包含拦截回复的同一个聊天里切换模型做对照。

8 规则维护与 YAML 操作

8.1 修改规则

rules/actions.py 中的 RULES 是规则定义入口，每项包含 id、name、reason、suggestion 和 patterns，以及 zh-TW 下的台湾繁体名称、原因和建议。MESSAGES 定义两种语言的标题与处理结果。patterns 由两种提示语言共用，修改文案不会改变匹配条件。匹配时先进行 NFKC 规范化和空白归一，再使用大小写不敏感的正则；命中列表按定义顺序去重展示。rules/demo_rules.co 决定命中后的返回与停止行为。

修改规则时，同步更新 rules/cases.json 的正反例。本版包含 58 条用例，并分别验证两种提示语言；如果增加用例，需要相应更新 tests/test_package.py 中的数量断言。先备份当前规则 ConfigMap，再渲染、测试和应用单个规则文件。

mkdir -p private
chmod 700 private
umask 077
oc get configmap nemo-demo-rules-config \
  -n nemo-guardrails-demo -o yaml \
  > private/rules-before-change.yaml
python3 scripts/render.py
python3 -m unittest discover -s tests -v
oc apply -f rendered/20-rules-configmap.yaml

等待 Operator 更新 NeMo Pod 并加载新规则，再执行 verify-service 与 verify，最后用新聊天复测。不要直接修改容器内文件；它们会在 Pod 重建后消失。不要为规则变更重新运行 install，也不要修改 guardrail-placeholder。

oc rollout status deployment/nemo-regex \
  -n nemo-guardrails-demo --timeout=300s
python3 scripts/cluster.py verify-service
python3 scripts/cluster.py verify

rollout status 可能在 Operator 尚未处理变更时返回旧部署就绪。应用后应确认出现新 Pod 或对应部署修订，再运行接口验收；接口结果才是规则生效的验收依据。需要回退规则时，应用保存的 rules-before-change.yaml，等待新部署后重跑验证。

8.2 不使用安装脚本时的 YAML 顺序

仍然先填写 settings.json 并运行 render.py。按照以下顺序执行；Secret 中必须使用目标 MaaS API key。该路径与 install 二选一，不要重复部署。

oc apply -f rendered/00-namespace.yaml
oc apply -f rendered/10-client-rbac.yaml

把 API key 保存为权限 0600 的 private/maas-api-key 文件，内容只包含 key。以文件创建 Secret，避免将 key 写入命令行历史。

oc create secret generic tinyllama-maas-api-key \
  -n nemo-guardrails-demo \
  --from-file=token=private/maas-api-key \
  --dry-run=client -o yaml | oc apply -f -

仅当配置了私有 MaaS CA 时，先应用 rendered/21-maas-ca.yaml。随后应用规则和 NeMo 资源。

oc apply -f rendered/20-rules-configmap.yaml
oc apply -f rendered/30-nemo.yaml
oc apply -f rendered/40-playground-service-ca.yaml

后续仍按第 4 至 7 节获取 token、配置 Playground、执行 trust 和验收。41-ogx-trust.patch.yaml 是补丁格式，不是可直接创建的资源；推荐使用 trust 脚本，因为它会保留原有 CA 列表。namespace、资源名如有修改，手工命令也要同步替换。

8.3 token 到期前或过期后的更新

更新分为“申请新 token”和“让 Playground 使用新凭据”两步。重新签发不会延长旧 token 的有效期，也不会自动更新端点；未到期的旧 token 不会仅因签发了新 token 就被撤销。建议在第 4.3 节记录的实际到期时间之前完成更新。

步骤 1：先完成第 3 节的配置初始化。新解压包不包含 settings.json，不能直接执行续期或 trust；复制并填写参数后运行 render.py。已有参数文件时核对原有项目、NeMo 名称、OGX 名称及 MaaS 完整基址，不改用其他项目的 Playground。随后确认 oc 当前集群，申请新的 30 天 token 并检查实际到期记录。此操作覆盖本地 token 文件，不修改集群中的端点配置。

oc whoami --show-server
python3 scripts/cluster.py token --duration=720h
cat private/nemo-playground-token-info.json

步骤 2：本手册核对的 RHOAI 3.5 自定义端点列表仅提供删除操作，没有直接编辑 API key 的入口。因此采用创建替代端点的方法：在 Gen AI studio → AI asset endpoints 中选择原 Playground 项目，点击 Create endpoint。沿用原 NeMo API 基址及模型 ID，使用新的唯一显示名称，例如 TinyLlama + NeMo Guardrails - renewed，将 private/nemo-playground-token.txt 中的新 token 填入 API key，不加 Bearer。暂时保留旧端点。

不要修改护栏命名空间中的 tinyllama-maas-api-key Secret：它保存的是 NeMo 调用 MaaS 的上游凭据，不是本次续期的 NeMo 访问 token。创建替代端点只新增 Dashboard 的端点登记，不重建 NeMo 服务或规则。

步骤 3：进入 Configure playground，取消勾选旧 NeMo 端点，勾选新建的替代端点。保留原始 MaaS/TinyLlama 的选择，把两个所选模型的 Max tokens 都设为 128，再保存配置并等待后端就绪。不要沿用新条目的默认 token 上限。

步骤 4：完成 Playground 配置后，等待后端就绪，补充证书信任，并使用刚生成的 token 验证服务链路。

python3 scripts/cluster.py wait-playground
python3 scripts/cluster.py trust
python3 scripts/cluster.py verify \
  --token-file private/nemo-playground-token.txt

步骤 5：刷新 Playground 并创建新聊天，选择新端点；保持原生输入/输出护栏开关关闭。先发送 NEMO_BLOCK_TEST，确认显示 DEMO-000 拦截说明，再发送 Hello，确认普通请求得到模型回答。这一步用于确认 Playground 保存的新凭据实际可用。不要在绑定旧端点的历史聊天里继续验证。

新端点完成页面验收后，如旧端点已无其他 Playground 使用，再到 AI asset endpoints 删除旧登记。删除旧登记并不等于撤销其 token，旧 token 仍按自己的实际到期时间失效。不要为 token 更新删除服务账号、NeMo 资源、规则 ConfigMap 或证书；也不需要重新运行 install。

8.4 已删除端点或 Playground 时恢复入口

本节适用于 NeMo 服务与配置仍存在，只删除了 Dashboard 自定义端点或 Playground 的情况。先完成第 3 节的参数初始化与渲染，再确认目标服务和账号仍在。以下使用默认名称；自定义名称需同步替换。

oc get nemoguardrails nemo-regex -n nemo-guardrails-demo
oc get service nemo-regex -n nemo-guardrails-demo
oc get serviceaccount nemo-playground-client -n nemo-guardrails-demo
python3 scripts/cluster.py verify-service

服务内部验证通过后，运行 token 生成新的 NeMo 访问凭据；按第 5 节在原项目创建 NeMo 自定义端点，选择现有 MaaS 模型与 NeMo 端点，并将两者 Max tokens 都设为 128。Playground 已删除时，需要重新点击 Configure 创建后端；仅保存 endpoint 不够。

python3 scripts/cluster.py token --duration=720h

完成界面配置后，核对同一项目中的 OGX 名称，依次运行 wait-playground、trust 和带 --token-file 的 verify，再用新聊天做第 7 节验收。这条恢复路径不运行 install，也不触碰上游 MaaS 凭据。若 NeMo 或服务账号本身已删除，应先核对剩余资源并按首次部署流程恢复，不能仅重建 Dashboard 入口。

8.5 升级部署包或切换提示语言

将新版解压到新目录，保留旧 settings.json、private/ 和自定义规则。把旧参数复制到新目录并核对；如需台湾繁体，在 settings.json 中设置 response_language 为 zh-TW，需要简体时设置为 zh-CN。先合并自己的规则改动，再执行第 8.1 节的备份、渲染、本地测试和单个 ConfigMap 应用步骤。不要用新版示例覆盖自定义策略。

等 Operator 加载新规则后，执行下面两项验收。现有 token 文件仍有效时继续使用；若保存在旧目录，可把 --token-file 改为原文件的完整路径。仅切换提示语言不需要重建 Playground、重新安装 NeMo 或签发新 token。

python3 scripts/cluster.py verify-service
python3 scripts/cluster.py verify \
  --token-file private/nemo-playground-token.txt

最后在 Playground 新建聊天，发送 NEMO_BLOCK_TEST，检查 zh-TW 显示“已攔截／觸發規則”，zh-CN 显示“已拦截／命中规则”；再测试普通问题。若提示语言仍旧，先核对 rendered/20-rules-configmap.yaml 的 RESPONSE_LANGUAGE 和实际 Pod 是否已加载新配置。

9 交付状态与使用限制

本包以已经完成的同版本功能演示为基础，重新整理为参数化的首次部署流程。交付前已执行本地规则测试、YAML 解析与嵌入源码一致性检查、脚本语法检查和文档排版检查。没有连接接收方目标集群，也没有声称已完成另一套离线集群的端到端部署；接收方应按第 7 节记录实际验收结果。

规则属于可解释的模式匹配示例。相同关键表达在引用或讨论场景也可能被匹配，同义改写、编码或混淆可能漏检。DLP-202 表示本演示的业务策略，不执行真实客户数据访问或权限判断。

不同环境应保持相同规则源码、NeMo/OGX 镜像版本、MaaS 模型 ID 和配置。输出文本与响应时间可能随模型采样、CPU 资源、会话历史及 MaaS 配额变化；这些变化不等于护栏规则失效。
